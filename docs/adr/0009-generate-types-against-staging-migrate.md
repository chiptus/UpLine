# Generate Supabase types against the staging migrate job

`database.types.ts` (and the edge-function copy under `supabase/functions/_shared/`) is generated by `scripts/gen-types.sh`, which introspects a live Postgres schema. New RPCs (e.g. `commit_schedule__compute_watermark`, added in PR #484) only appear in the generated types once that script is re-run against a database that already has the new migrations applied.

We generate types in a dedicated `_regenerate_types.yml` reusable workflow, called as its own `types` job from `deploy-staging.yml` right after the `migrate` job succeeds against staging, and commit the regenerated files straight back to the PR branch (as a bot commit), rather than spinning up a separate ephemeral local Postgres in CI to generate against.

We generate against the staging schema (rather than an independent CI job spinning up its own Postgres) for two reasons:

- **Reuses infra we already trust.** The regeneration job links to the same staging project `migrate` just pushed to and has the credentials; generating types there means generating against the exact schema that's about to become real staging, rather than a separately-provisioned local Postgres that could theoretically diverge in how Supabase's remote introspection resolves types.
- **The staging label/lock already serializes this.** Only one PR can hold the `staging` label at a time (`staging-lock.yml`), and merging is already blocked until that PR's migrate job succeeds. Piggybacking on it means the type-regeneration commit is naturally serialized too — no risk of two PRs racing to write `database.types.ts` — and no PR can merge with stale types, since merging already requires this job to have run.

Regeneration is a separate job (`_regenerate_types.yml`), not a step inside `_db_migrate.yml`, so that only it needs the `contents: write` permission to push the regenerated-types commit — `migrate` itself never touches git history and stays read-only. This follows the repo's existing pattern of composing sibling reusable workflows (`_db_migrate.yml`, `_deploy_edge_functions.yml`) from `deploy-staging.yml` rather than folding unrelated concerns into one job.

A PR that touches migrations but doesn't yet hold the `staging` label gets no type regeneration until it acquires the lock — this is fine, since it can't merge yet either way.

There's no separate "fail if types are stale" check: the regenerate-and-commit step's own failure (e.g. push rejected) is the only way this can go wrong, and it already fails the job.

Edge functions typing their Supabase client with `Database` (`createClient<Database>(...)`) is the convention going forward for new/touched code, but existing untyped clients (`_shared/auth.ts`, `sync-artist-data`, `commit-schedule`) are left as-is — backfilled opportunistically whenever those files are next touched, not in a dedicated migration PR.
