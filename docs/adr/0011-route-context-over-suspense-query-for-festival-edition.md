# Route context, not per-consumer `useSuspenseQuery`, for festival/edition reads

`festival` and `edition` are read via TanStack Router's route context, not via a shared `useSuspenseQuery` hook called by every consumer. `src/routes/festivals/$festivalSlug.tsx` and `.../editions/$editionSlug.tsx` each fetch their entity in `beforeLoad` (`context.queryClient.ensureQueryData(festivalBySlugQuery(...))` / `editionBySlugQuery(...)`) and return it as route context, which TanStack Router merges up the route tree so the edition route's context carries both. `$festivalSlug.tsx`'s own `component` is just `() => <Outlet />` — it doesn't read `festival` itself. `$editionSlug.tsx`'s `component` is `EditionLayout` (the substantial header/tab-nav wrapper, lines 82–103), which reads `{ festival, edition }` with `Route.useRouteContext()`. Components nested arbitrarily deep under the edition route (`TabNavigation`, `SetInfoCard`, `NonMusicSetBanner`, `MultiArtistSetInfoCard`, etc.) read the same context with `useRouteContext({ from: "/festivals/$festivalSlug/editions/$editionSlug" })` — type-checked against that route id via the generated route tree, not untyped. There is no `FestivalLayout`/`FestivalEditionContext` in the codebase.

An earlier ticket (UPL-9) proposed the opposite: delete a (by-then-already-gone) `FestivalEditionContext`, add a shared `useEditionSuspenseQuery()` hook, and have every consumer call `useSuspenseQuery(festivalBySlugQuery(...))` / `editionBySlugQuery(...)` directly instead of reading route context. That plan predates this ADR and was written against a codebase state — a `Context.Provider` wrapping route components — that other work had already replaced with `beforeLoad` + route context before the ticket was picked up. This ADR records the maintainer's decision (2026-09-12) to keep the route-context shape rather than retrofit the Suspense-query one, so the plan isn't re-attempted against a spec the code no longer matches.

## Considered Options

- **Route context via `beforeLoad` (chosen).** One fetch per route match, cached on `context.queryClient` and exposed to the whole subtree; each consumer's read is a plain context lookup, not a second query subscription. `notFoundComponent` and `onError` on the route already handle the not-found/error path in one place.
- **Per-consumer `useSuspenseQuery(festivalBySlugQuery(...))`.** Every one of the ~17 nested consumers would re-run `useParams` + its own suspense query against the cache instead of reading the value `beforeLoad` already resolved once for the route match. Functionally equivalent once the query is cache-warm (TanStack Query dedupes identical keys), but it trades one `beforeLoad` fetch + N context reads for N cache-hit query subscriptions, with no behavioral upside identified — the original ticket's justification (delete a context provider) no longer applies once the provider is already gone.

## Consequences

- New consumers under `/festivals/$festivalSlug` or `/festivals/$festivalSlug/editions/$editionSlug` should read `festival`/`edition` via `useRouteContext({ from: <route id> })` (or `Route.useRouteContext()` for the route's own `component`), not by calling `festivalBySlugQuery`/`editionBySlugQuery` directly.
- `EditionSelection` (the component for route `/festivals/$festivalSlug/`, in `src/routes/festivals/$festivalSlug/index.tsx`, which has no `editionSlug`) is the one place that reads `festival` outside the edition route context, since there is no edition to attach it to.
- If a future change wants per-consumer Suspense queries instead (e.g. to avoid over-fetching in `beforeLoad` for a route with many rarely-visited children), that's a new decision to record here, not a return to the pre-existing UPL-9 plan.
